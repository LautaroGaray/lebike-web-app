TODO - Contratos de backend pendientes de confirmar (módulo Recepciones)

Los ejemplos en examples-frontend/request/receipts/*.json son plantillas genéricas que no
coinciden con el objeto Receipt real (el que sí está bien documentado en las respuestas de
examples-frontend/receipts/*.json). Se adaptaron los payloads del frontend para que tengan
sentido con ese objeto. Falta que backend confirme/implemente estos contratos:

1. POST /receipts/findAll
   - Ejemplo original: { page, size, criteria: { q } }
   - Payload que envía el frontend: { page: number, size: number, criteria: object }
   - El filtro multiselect de depósitos se resuelve hoy en el cliente sobre el listado
     completo devuelto por el mock; falta definir si el filtrado/paginado real será
     server-side.

2. POST /receipts/register
   - Ejemplo original: { userId, warehouseId, items: [{ articleId, quantity, price }], total }
     (parece copiado de un flujo de órdenes de compra, no de recepciones)
   - Payload que envía el frontend: { origin, destiny, description, userId, articleIds: number[] }

3. POST /receipts/edit
   - Ejemplo original: { id, changes: { name, active } }
   - Payload que envía el frontend: { id, status, origin, destiny, description }

4. POST /receipts/history
   - Ejemplo original: { userId, from, to } (rango de fechas)
   - La respuesta de ejemplo es el historial de UNA recepción puntual, no de un usuario/rango.
   - Payload que envía el frontend: { receiptId: number }

5. GET /warehouses
   - No hay un endpoint documentado específicamente para poblar el multiselect de depósitos
     ni para mapear código -> nombre en la grilla. Se asumió GET /warehouses sin body,
     siguiendo el mismo patrón que GET /users y GET /modules/user.

6. Catálogo de artículos para el alta de recepciones
   - No existe un endpoint "listar todos los artículos" (solo /articles/findByCriteria, que
     en el ejemplo devuelve un único artículo, no un array). El formulario de alta de
     recepción pide por ahora los IDs de artículo escritos a mano (separados por coma).
   - Falta un endpoint tipo /articles/findAll para poder armar un selector por nombre/SKU.

7. Importes y datos comerciales en respuestas de receipts
    - Todas las respuestas que devuelven una Receipt deben incluir `price: number`, que es
       el importe total del documento. El frontend acumula ese valor para las tarjetas de
       recepciones nuevas, enviadas y recibidas; no recalcula totales desde los artículos.
    - Cada objeto dentro de `details` debe incluir `salePrice: number` y `supplier: string`,
       igual que el contrato de artículos. El detalle de la recepción usa esos campos para
       mostrar precio de venta y proveedor.

Confirmar estos puntos con backend antes de integrar contra el ambiente real (dev/prod).
